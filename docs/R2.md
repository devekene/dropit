# Cloudflare R2 setup and verification

DropIt stores object bytes in a private Cloudflare R2 bucket. The API uses an
S3-compatible object read/write credential to sign exact-key requests, verify
objects with `HEAD`, and delete objects. The browser receives only short-lived
presigned URLs and never receives the R2 secret access key.

## Local environment

Copy the placeholders from `apps/api/.env.example` into the ignored
`apps/api/.env.local` file:

```dotenv
S3_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
S3_REGION=auto
S3_BUCKET=<private-bucket-name>
S3_ACCESS_KEY_ID=<object-read-write-access-key-id>
S3_SECRET_ACCESS_KEY=<object-read-write-secret-access-key>
APP_ORIGIN=http://127.0.0.1:3000
```

Use a bucket-scoped Object Read & Write token for the application. It needs
object `PUT`, `GET`/`HEAD`, and `DELETE`; it does not need bucket administration
or listing. Keep bucket configuration in the Cloudflare dashboard or a separate
administrative workflow. Do not commit either credential or copy it into the web
application.

## Bucket CORS

Keep the bucket private and add a CORS policy for each exact deployed web origin.
For local development, replace the origin below only if `APP_ORIGIN` differs:

```json
[
  {
    "AllowedOrigins": ["http://127.0.0.1:3000"],
    "AllowedMethods": ["GET", "PUT", "HEAD"],
    "AllowedHeaders": ["Content-Type", "Content-MD5"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

Do not use `*` for origins. Add staging and production as explicit policies with
their HTTPS origins. `Content-Type` and optional `Content-MD5` must remain
allowed because they are signed upload headers. `ETag` is exposed for browser
diagnostics; the API still performs the authoritative `HEAD` verification.

## Signing and verification behavior

- Object keys are random and server-owned:
  `v1/transfers/<transfer-uuid>/files/<file-uuid>/<random-uuid>`.
- Every storage operation checks that the key embeds the same transfer and file
  IDs as the request. A key for another transfer or file cannot be signed.
- Upload URLs expire in at most 300 seconds. Download URLs expire in at most 60
  seconds and force `application/octet-stream` plus attachment disposition.
- Upload signing binds the expected content length, content type, and optional
  `Content-MD5`. MIME remains untrusted metadata.
- A successful browser `PUT` is not completion. The API must `HEAD` the exact
  key and compare actual length and the optional checksum before recording the
  file as verified or allowing a transfer to become READY.
- A mismatched object must be rejected and deleted by the completion workflow.
  Presigned PUT is not treated as a hard content-length-range control.

## Provider integration test

Run the isolated live test only against a disposable development bucket:

```sh
pnpm test:r2
```

The test creates random objects, exercises browser CORS preflight, direct upload,
signed download, `HEAD`, deletion, wrong MIME, bad checksum, size mismatch, and
expired URL behavior, then deletes all test objects in `finally`. The normal
`pnpm test` command excludes this credentialed provider test.
